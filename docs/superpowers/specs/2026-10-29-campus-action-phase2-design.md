# 校園通知待辦助手：第二階段「公告行動資訊卡」設計

日期：2026-10-29（Asia/Taipei）

狀態：使用者已同意第二階段方向。本書面規格待審閱；尚未開始產品實作、資料庫遷移或部署。基準為第一階段完成版本 `818e0e9`。

## 先看這五項決定

1. 公開、私人 Gmail、合成示範的詳情頁共用行動卡格式；來源與讀取權限仍分開。
2. 日期與行動優先沿用既有規則，資料不足一律「待確認」；不因標題、分類或學生身分推斷符合資格。
3. 既有 AI 結果可供核對，但多人網站目前沒有啟用 AI。本階段不呼叫新 AI、不掛載單人 API、不擷取新全文。
4. 公開修正存在此裝置；私人 Gmail 修正依登入帳號保存。原始解析、原文依據與修正歷史分開，來源版本改變時不自動沿用舊修正。
5. 私人修正需要新增兩張小型資料表及 migration `0007`，只在獨立測試庫驗證；不執行正式遷移。本階段不實作待辦或行事曆。

## 1. 使用者目標、範圍與現況

目標是讓一般高科大學生看完公告後，知道「公告說要做什麼、何時截止、活動何時發生、哪些資訊仍需核對」。卡片提供資訊，不代替資格審查，也不將系統辨識等同於使用者承諾參加或加入待辦。

本次為架構型變更：新增可追溯的衍生資訊介面與個人修正保存。沿用第一階段 FastAPI／Jinja、私人帳號隔離、官方 URL 驗證、既有 CSS 與原生 JavaScript，不引入框架、服務或新套件。

現況已從程式確認：

- `date_parser.parse_dates` 已區分 `event_date`／`deadline`，保留原日期文字、位置、角色、年份推定與警告。但角色判斷有啟發式，不能將所有候選日期當成確定事件日期。
- 私人 `Announcement` 已有原文、日期證據、摘要、行動旗標；現行多人詳情未呈現完整日期依據。
- `AnalysisOutput` 已有摘要、行動依據、活動／截止證據，沒有適用對象或材料欄位。`ai_analyzer` 已驗證逐字引用及日期；`AnalysisService` 使用的是單人資料模型，不具多人帳號範圍。
- 多人 `Analysis`／`Scrape` 表目前是保留／未啟用用途。不能宣稱多人服務已有可用 AI 分析，更不能直接掛載單人分析或擷取 API。
- 公開表只有來源標題、摘要、發布時間與連結；摘要可能截短，未保存完整官方正文。私人重新解析會刪除並重建公告列，不能只靠公告 ID 與 CASCADE 保存修正歷史。

## 2. 選定方案與取捨

選擇「純函式建立卡片＋獨立修正層」。讀取不變更原公告、日期欄位或 AI 紀錄；只有使用者明確儲存才建立修正資料。

沒有選擇直接覆寫公告欄位：會丟失原解析，也可能讓一人的修正影響公開讀者。沒有選擇所有內容放瀏覽器：私人 Gmail 會留在共用裝置，難以維持登出與帳號隔離。沒有選擇所有公開修正強制登入：會阻斷匿名閱讀的主要流程。

公開採原生 IndexedDB 裝置儲存。相較單一 localStorage JSON，IndexedDB 交易可在同一筆紀錄內核對修正版本並原子寫入，降低多分頁覆寫風險；代價是儲存模組稍多，且無 JavaScript／儲存被封鎖時只能閱讀卡片。這不是新外部服務。

私人採既有 SQLAlchemy／Alembic 與登入帳號保存；支援同帳號跨裝置讀取，代價是增加資料表與後續部署前遷移驗收。修正會明示保存至本站，不送至 Gmail 或 AI。

## 3. 行動卡內容與狀態

卡片位於詳情標題之後、原文／來源摘要之前。首頁與清單不在此階段改成待辦總覽，也不新增每頁大量分析查詢。

| 欄位 | 呈現規則 |
| --- | --- |
| 摘要 | 有來源摘要則標「來源摘要／節錄」；私人無可靠摘要時以原文節錄，標示可展開全文。既有 AI 摘要另標來源，不混成官方摘要 |
| 需要採取的行動 | 顯示可核對的申請、報名、繳件等原文片段；沒有可靠判斷顯示「待確認」。辨識到行動不代表本人必須處理 |
| 適用對象／所需材料 | 僅採明示的對象、資格、材料段落；不足顯示「待確認」。不以科系、分類、寄件單位或標題代替資格判斷 |
| 報名／申請／繳件截止 | 獨立日期欄位，依原文標示截止種類；只有一般截止時標「截止事項（類型待確認）」，不一律稱為報名截止 |
| 活動日期／官方連結 | 活動日期與截止分欄；發布／收件時間仍在來源區。官方連結使用現有安全驗證，不讓個人修正替換官方連結 |

每個衍生欄位包含值、狀態、來源種類、原文引用、引用所屬文字、解析版本與必要警告。資料狀態至少包含 `supported`（規則與原文支持）、`pending`（待確認）、`user_confirmed`（使用者修正／確認）、`stale`（來源版本已改變）。值缺少不等於否定，未知行動不得顯示「不需要處理」。

「查看依據」展開實際原文片段及上下文；公開證據清楚標為「來源標題」或「來源摘要」，私人標為「郵件公告原文」。逐字引文不可冒稱完整官方正文。索引位置以實際解析文字為準，不把既有主旨座標直接套到整段郵件原文。

公開連結沿用高科大網域驗證。私人郵件的既有 `safe_url` 只證明 URL 格式可安全呈現，不能證明外站或短網址為官方；非高科大網域須標「公告提供的連結，官方性待確認」，不因出現在郵件就加上官方認證。

## 4. 日期與行動的驗證規則

### 4.1 沿用解析器，增加卡片層的確認門檻

`parse_dates` 產生候選與證據；新增卡片層檢查上下文角色、歧義及年份狀態，不改寫整個單人解析流程，也不修改既有儲存日期以配合介面。

- 發布日期、公告更新日及收件日不能轉成活動或報名截止。只有明確角色及原文支持的候選才成為 `supported`。
- 私人省略年份可沿用收件年候選，但卡片標「年份依收件年推定，待確認」。公開不以今天或發布年份猜缺漏年份。
- 多個不同截止、日期範圍、跨年語意、無效日期或角色衝突時，保留所有候選與警告；不自行挑最早、最晚或最近的一個。
- 民國年、完整西元年與合法日期沿用既有解析。日曆日期保留為日期，不轉 UTC 午夜。顯示與日後截止狀態使用 Asia/Taipei，不用瀏覽器所在地推算今天。
- 本階段不新增通用時間／時段解析。原文有時間時保留引用並標時間待核對；不能把「尚未解析時間」誤當「原文沒有時間」，以免第四階段錯誤匯出全天事件。

既有 `date_evidence`、日期欄位與新解析結果皆保留供比較。只有在目前來源文字能重現日期及角色時才用作確定值；未能重新驗證的舊值標「既有解析，待確認」，不悄悄刪除，也不直接成為後續確定期限。

### 4.2 行動、對象與材料

規則先辨識明確的指示／受理語句與標示段落，例如「請於…前報名」、「申請對象：」、「應備文件：」。只出現「報名資訊」、「錄取名單」或分類為獎學金，不能直接判定須行動。

否定語句必須保留；「無須報名」不能被當成要求報名。若同時另有繳件要求，兩項分開呈現，不讓一個否定句取消所有行動。截止已過只描述該日期已過，不判定使用者失去所有資格，也不捏造其他期限。

第一版只擷取清楚可界定的條款／段落；模糊的敘述留作原文待確認，不做複雜推薦。對象區固定提示「公告列出的適用對象不代表你已符合資格，請核對完整條件」。沒有「你符合資格」或個人資格推定欄位。

### 4.3 既有 AI 結果

只讀取目前帳號、目前公告的多人 Analysis 紀錄，或該公告既有欄位；不讀單人資料庫、不自動匯入、不產生新分析。無結果時，規則卡片照常工作。

完成狀態、輸出結構、版本與來源關聯需檢查。既有 `input_hash` 包含舊服務的可變快照欄位，不能假設可由目前公告重算而證明版本一致。缺少可驗證來源版本時標「既有 AI 結果，版本／來源一致性待確認」，放在可展開的參考區。

AI 日期／行動引用需逐字存在於目前來源，日期還需通過規則與角色驗證。只有 AI 的主張不能升級成確定日期、資格、材料或行動。既有自由生成摘要標「AI 摘要，請核對來源」，不把它當成新增事實來源；查不到證據的資格與材料保持待確認。

失敗、損壞、過期或不支援版本的結果不阻斷閱讀；保留診斷狀態，不輸出供應商原始錯誤／金鑰。若私人舊補充網頁內容沒有可信版本／擷取來源，僅列參考，不混入目前證據。

## 5. 個人修正與歷史

可修正摘要、行動文字／判斷、適用對象、材料、截止種類與日期、活動日期；不能改官方來源、原文、帳號擁有者或把私人資料發布至公開區。

表單清楚區分「沿用系統」、「改為我的值」、「標為待確認」。不以空字串同時代表清除與沿用。日期必須是真實 ISO 日曆日期；使用者確認時勾選已核對原文。若附帶文字不是目前來源的逐字片段，標為「個人補充，系統未驗證來源」，不冒稱官方證據。

修正永遠標示「我的修正」與保存時間，不改系統原解析。手動日期確認是使用者的確認，不標為系統驗證；第四階段匯出前仍需再次核對。對象修正仍只是公告對象描述，不會產生本人符合資格的狀態。

每次儲存新增修正版本。「恢復系統資訊」也新增重設版本，保留舊修正可查。原始卡片快照包含來源文字、原解析／證據、使用的 AI 參考與版本；解析結果／來源改變時，舊修正不自動覆蓋新卡片，顯示「來源或解析版本已變更，請重新核對」。使用者可比較後再次儲存，不能只把舊版本標為最新。

版本定義：`source_hash` 對來源種類、穩定來源身份、標題、實際文字、來源 URL 及相關時間錨點的規範化 JSON 計算 SHA-256；時間錨點轉 UTC，排除抓取／讀取時間與公告列的 `updated_at`。`baseline_hash` 再包含卡片解析版本與實際採用的 AI 參考識別／內容 hash，不由客戶端決定私人版本。相同內容重讀不產生新版本。

輸入界線：個人摘要最多 160 字，行動／對象／材料各最多 1,200 字，個人引用各最多 2,000 字；超過上限顯示錯誤，不截斷後儲存。日期與截止種類使用固定格式／白名單，private POST 原始表單總量上限 128 KiB；解析後仍檢查每欄長度、重複欄位及未知欄位。

### 5.1 公開公告：裝置保存

在首次儲存前明示：「僅存在此瀏覽器與裝置，不隨 Google 帳號切換；共用此瀏覽器的人可能看到，請勿填入私人郵件內容。」不呼叫登入或上傳端點，不設 Cookie 追蹤，不在 GET URL 放修正內容。

IndexedDB 使用獨立應用名稱及版本，紀錄以 `source_key + canonical_url` 的穩定來源鍵識別；不以易變的公告數字 ID 跨來源認同。每筆包含原始快照、來源／解析版本及追加的修正歷史。這只識別同一公開來源，不是第五階段跨來源去重。

每筆裝置紀錄包含依 baseline hash 識別的多個原始快照與引用該快照的修正版本；來源改變後，儲存新修正會新增快照，不覆蓋舊快照。private 卡片路徑不得開啟此裝置儲存模組；即使共用顯示元件，也需先檢查來源種類。

交易內核對預期修正版本，再讀改寫同一紀錄。儲存額度不足、被封鎖、損壞或多分頁衝突時，保留最後成功版本、提示未保存，暫存表單內容讓使用者重試；不得默默清空或把失敗說成成功。清除瀏覽器資料會遺失這些修正，不承諾跨裝置同步。

不自動保存每次閱讀或輸入。只有明確按儲存才持久化。提供清除此公告裝置修正的操作，說明會刪除本機修正歷史並由使用者確認；不會刪除公開公告或影響其他讀者。

### 5.2 私人 Gmail：帳號保存

使用既有 Session 與 ownership 查詢，儲存前提示：「依目前登入帳號保存至本站，不會修改 Gmail，也不會送交 AI。」私人原文、快照與修正不寫入 IndexedDB、localStorage、sessionStorage 或 Service Worker 快取。

新增兩張表，僅管理自己的資料：

| 表 | 內容與關聯 |
| --- | --- |
| `private_action_snapshots` | `id/user_id/email_id/source_index/source_fingerprint/source_hash/baseline_hash/parser_version/source_text/source_metadata/original_card/created_at`，另有修正版本計數。原始內容欄位不可被修正覆寫；相同基準只建一次 |
| `private_action_revisions` | `id/user_id/snapshot_id/revision/operation/overrides/created_at`，追加式修正；每個 snapshot 的 revision 唯一 |

快照以 `(user_id, email_id)` 複合 FK 綁定本人 Email；修正以 `(user_id, snapshot_id)` 複合 FK 綁定本人快照，對應唯一約束須一併建立。帳號／郵件刪除時 CASCADE 清除自己的快照及修正，不能影響公開公告或別人。

快照唯一鍵為 `(user_id, email_id, source_index, source_fingerprint, baseline_hash)`，另建立 `(user_id, id)` 唯一約束供複合 FK 使用。項目索引不得為負；修正版本從 1 開始，操作只接受 save／reset。歷史不因恢復系統資訊而刪除。

快照不對易重建的 Announcement ID 設 CASCADE 外鍵；記錄其 ID 僅供追溯，身份還需郵件、項目索引、來源指紋與基準版本。重新解析後，只有來源身份與基準完全吻合才可套用；索引或指紋改變時不得只因標題相同而套用。歷史快照仍附在本人原郵件，供目前該郵件的詳情入口查看，避免重新解析刪除歷史。

GET 卡片不建立快照或修正。首次私人儲存於同一交易驗證本人公告與來源版本、建立快照及追加修正；之後使用預期 revision 與基準 hash 阻擋覆寫。寫入與既有同步／刪除遵循 User 優先的鎖定順序；版本已改變回 409，沒有寫入則不顯示成功。

新 POST 儲存／重設路由只接受本人 Session、既有 HMAC CSRF、同來源檢查、白名單欄位與有上限的表單。不能接受客戶端聲稱的 owner、原始快照或可信解析結果。來源 hash／擁有者與修正內容都由伺服器驗證。

私人儲存錯誤以繁中保留輸入並提示；不同帳號、過期 Session、CSRF 失敗與不存在資料不可回傳別人快照。登出後伺服器 Session 失效，帳號切換後不能讀舊帳號修正。資料刪除沿用既有帳號刪除流程與備份保留說明，不宣稱即時清除所有備份。

### 5.3 合成示範

沿用相同行動卡及規則，未知日期／摘要仍是未知。可體驗修正與恢復，但只保存在目前頁面記憶體，重新載入即重設；不寫入任何持久化裝置區或伺服器。每頁明示此限制，保留合成警語。不得將示範修正混入真實公告。

## 6. 介面、錯誤與實際修改範圍

手機版先呈現摘要、行動與截止／活動日期，再呈現對象與材料；各欄有明確標籤。依據與原始解析可展開，編輯表單只在使用者選擇修正時出現。未知值顯示文字，不以顏色單獨表達狀態。320／390px、鍵盤焦點與表單錯誤都要驗收，沿用既有配色。

無 JavaScript 時仍可讀取伺服器建立的卡片、原文與依據；公開持久化修正需 JavaScript／IndexedDB，私人可用 HTML POST 表單。載入私人修正失敗時不假裝從未有修正；回應需告知目前資料讀取不完整，避免讓使用者誤覆寫歷史。

| 檔案／區域 | 修改責任 |
| --- | --- |
| 新增 `app/services/action_cards.py`、`app/schemas/action_cards.py` | 純來源轉接、規則／日期證據檢查、卡片狀態與修正白名單；沿用 `date_parser`，不加入外部呼叫 |
| `app/api/public_announcements.py`、`user_announcements.py`、`demo.py` | 在各自既有權限下建立詳情卡片；私人依 owner 讀已有 AI 與修正；公開與示範仍不解析 Session |
| 新增 `app/models/action_cards.py`、`app/services/action_card_corrections.py`、`app/api/action_card_corrections.py`、migration `0007` | 私人快照／修正、版本衝突、本人歷史、CSRF 與帳號刪除關聯；更新 schema revision／註冊與測試契約 |

具體私人路由為 `POST /announcements/{id}/action-card/corrections`（儲存或重設）與 `GET /action-cards/history/{snapshot_id}`（本人歷史）。公開與示範不增加儲存 API。新表單頁面需要配合既有 Referrer-Policy 的 same-origin／CSRF Origin 行為，不能為通過表單而放寬 Origin:null 驗證。

## 7. 驗收條件

1. **日期可驗證：**民國年、完整西元年、省略年、跨年、無效日期、多日期／範圍、發布日期混入、活動／截止分離與台北日期邊界都有回歸案例；原文與警告保留，推定／衝突不偽裝確定。
2. **欄位有證據：**否定報名但另須繳件、模糊行動、對象不等於本人資格、缺材料、截短摘要、未知／過期 AI、同字串不同上下文與惡意 HTML 都有案例；沒有 Gmail／AI 金鑰仍可用。
3. **修正不丟資料：**新修正、恢復系統、來源改變、解析版本改變、重新解析重建公告、無效表單及儲存失敗都保留原快照／歷史；多分頁及同帳號併發不靜默覆寫。
4. **隱私與隔離：**匿名／有效／偽造 Cookie 的公開卡片不讀私人 Session；私人讀寫與歷史均驗證 owner，CSRF／跨來源／過期 Session 被拒絕；帳號刪除只刪本人新資料，示範重載不保留修正。
5. **環境與回歸：**0006→0007 在合成 SQLite 驗證不修改既有資料，含 FK／重跑／回復測試；PostgreSQL 實機只用明確專用測試庫，未提供就列 skipped。裝置交易、重載保存、額度錯誤及兩分頁衝突需實際瀏覽器驗證，再跑相符的 Node 與完整 pytest。

所有 GET 讀取不觸發 Gmail、AI、全文擷取、資料遷移或修正寫入。私人及公開來源不合併；Service Worker 不快取卡片、快照或私人頁面。測試只用合成資料；不複製正式連線、token 或 `.env` 至工作區。

## 8. 後續階段與發布界線

第三階段的「我的待辦」將消費卡片狀態及明確的使用者操作，而不是把 `requires_action` 直接當成待辦。可沿用本階段已說明的公開裝置／私人帳號邊界，但待辦格式、稍後時間與首頁排序仍由第三階段獨立設計。

第四階段可讀來源角色、日期確認／推定狀態與原文時間狀態，不能直接把卡片日期視為可匯出。第五階段可利用來源鍵與 hash，但本階段的「修正基準版本變更」不是跨來源合併或完整公告歷史追蹤。

新增 migration 僅編寫及在獨立測試庫執行；不改正式庫、不部署、不推送部署分支、不修改 OAuth、不新增付費或排程服務。正式發布前須另行確認備份、0007 遷移與 PostgreSQL 驗收；降級若刪除新表會遺失修正，不能當成可直接執行的正式回復方案。
